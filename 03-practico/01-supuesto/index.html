8  Supuesto práctico

8.1 Introducción al supuesto práctico

Este documento es un resumen de información relevante para la preparación de la parte del supuesto práctico del ejercicio práctico de acceso al Cuerpo Superior de Sistemas y Tecnologías de la Información de la Administración del Estado (CSSTIAE).

8.1.1 Material a llevar al consejo práctico

Material para llevar:

  • 2 bolígrafos
  • Corrector ortográfico
  • Subrayadores de colores
  • Lapicero
  • Goma de borrar
  • Cuaderno, hojas o portátil para realizar el volcado

8.1.2 Consejos para el supuesto práctico

Resumen de consejos:

  • Leer las preguntas antes de leer el enunciado completo.
  • Subrayar los conceptos del exámen
  • Emplear una hoja para cada ejercicio. No penaliza el número de hojas empleadas, y el emplear hojas independientes permite alargar la resolución del ejercicio en el caso necesario.

En la mayoría de tribunales, si escribes en las hojas del enunciado del supuesto práctico no las podrás sacar posteriormente. No contar con el enunciado dificulta la realización del volcado, por lo que no es un buen consejo.

Por el contrario, emplear subrayadores es compatible con sacar la hoja del enunciado. Algunos candidatos emplean varios colores para marcar distintas categorías de palabras claves, como por ejemplo actores, acciones, etc.

Una propuesta de subrayado de colores puede ser:

Significado Color sugerido
Actor / Sistema Azul
Entidad de datos Verde
Funcionalidad Naranja
Normativa Rojo
Cuestiones de interés Amarillo

Se podría distinguir con distinto color los actores internos y externos.

8.2.1.1 Diagrama de casos de uso

Nota📋 Marco de referencia
  • Temas
      1. Análisis de sistemas y metodologías ágiles
  • Referencias
    • Métrica v3. PAe.
    • Cillero, Manuel. Casos de uso en Métrica 3.

El diagrama de casos de uso…

Los actores se corresponden con tipologías de usuarios, organismos o sistemas externos que interactúen con el sistema.

Los casos de uso se corresponden con las funcionalidades del sistema detectadas.

La relación «include» entre casos de uso se representa con una flecha discontinua y apunta desde el caso de uso que incluye hacia el caso de uso incluido. Indica que el caso de uso incluido es obligatorio para el caso de uso que incluye. Un ejemplo es que para realizar una compra (incluye) es necesario realizar el pago (incluido).

Se puede usar cuando una funcionalidad es común a varios casos de uso, y se quiere evitar repetirla en cada caso de uso.

La relación «extend» entre casos de uso se representa con una flecha discontinua y apunta desde el caso de uso que extiende hacia el caso de uso extendido. Indica que el caso de uso es opcional para el caso extendido, y que se ejecuta bajo ciertas condiciones. Un ejemplo es imprimir un recibo (extensión) tras realizar una compra (extendido).

Cuando se emplea una relación «include» o

El sistema engloba los casos de uso, representándose con un rectángulo.

Consejos:

  • Incluir alguna relación «include» y «extend» entre casos de uso, para demostrar al tribunal la capacidad de trabajar con estos conceptos.

8.2.1.2 Diagrama de flujo de datos

Nota📋 Marco de referencia
  • Temas
      1. Análisis dinámico de sistemas
  • Referencias
    • Cillero, Manuel. Diagrama de Flujos de Datos en Métrica 3

Diagrama de Flujo de Datos (DFD) es un diagrama que representa el flujo de información entre los distintos elementos de un sistema.

El DFD consta de varios niveles de detalles, numerados de 0 a n, donde 0 es el nivel más alto y n es el nivel más bajo. El nivel 0 es conocido como diagrama de contexto, y representa el sistema como un único proceso que interactúa con elementos externos. Los niveles 1 a n van aumentando el nivel de detalle del sistema y procesos de manera jerárquica.

8.2.2 Arquitecturas de sistemas

8.2.2.1 Dominios/subdominios funcionales

Nota📝 Apariciones en examen

Conv. 2023.

La identificación de dominios/subdominios funcionales se refiere a dividir el sistema en grandes áreas funcionales, agrupando las funciones que persiguen un mismo objetivo de negocio.

8.2.2.2 Arquitectura conceptual

En la arquitectura conceptual se pueden agrupar las acciones a realizar de manera pública por un lado, las acciones del área por otro, y añadir un proceso pasarela que sea autenticación de usuario y que conecte ambos grupos.

8.2.2.3 Arquitectura de sistemas

La arquitectura de sistemas (en plural) se refiere a un diagrama de alto nivel sobre la interacción de distintos sistemas.

8.2.2.4 Arquitectura lógica

Nota📝 Apariciones en examen

Convocatorias: 2023.

La arquitectura lógica, a la que también se pueden referir como arquitectura de sistema (en singular), representa las distintas cpas que posee el sistema.

Ejemplos de modelos de arquitectura de sistemas:

  • Modelo-vista-controlador (MVC)
  • Microservicios

MVC

Nota📋 Marco de referencia
  • Referencias
    • https://runmodule.com/2024/12/03/mvc-architecture/

En el modelo-vista-controlador existiría una capa de presentación, otra de aplicación o negocio y una última de datos.

Se suelen representar la base de datos, el directorio y el gestor documental para almacenar datos.

Propuesta de niveles principales:

  • Presentación
  • Lógica de negocio
  • Acceso a datos y servicios

Microservicios

Nota📋 Marco de referencia
  • Referencias
    • https://runmodule.com/2024/12/03/microservices/

En microservicios se suele pintar un API gateway al inicio de la lógica de negocio.

El API gateway son el punto de entrada a los microservicios. Puede contenter una API separada para la web, que podría ser reactiva (diseño), y una de móvil.

Una aplicación de móvil se conecta directamente con el backend, ya que es la app instalada en el móvil quien lleva la carga del frontend.

Habitualmente en sector público se usa la integración de lado de servidor (server-side integration). Esto se hace a través de un front-end UI composer.

De manera transversal:

  • Administración
  • Seguridad
  • Monitorización

Se puede usar una CDN a la parte que sea más común a todos los usuarios, como contenido estático (una noticia, etc.).

8.2.2.5 Arquitectura física

  • Referencias
    • https://runmodule.com/2027/03/30/network-architecture/

La arquitectura física implica especificar los componentes técnicos a emplear, ya sean físicos o virtuales.

Elementos que deben considerarse en la arquitectura física:

  • Servidores
  • Balanceadores de carga
  • Cortafuegos
  • Redes de área local (LAN)
  • Proxy
  • Proxy inverso
  • Bases de datos

Los servicios comunes y transversales de las AAPP se ofrecen a través de la red SARA.

El sistema debe conectarse a la red SARA a través del cortafuegos interno de la red petrimetral (o zona desmilitarizada).

Para acceder a la red sTesta se puee conectar directamente a través de la red SARA.

Para las bases de datos se debe elegir entre bases de datos relacionales o bases de datos NoSQL.

Se suele usar datos NoSQL cuando el volumen es alto y se busca escalabilidad horizontal (columna ancha), cuando se busca flexibilidad estructural respecto a tablas (documental, grafal) o se requiere simplicidad y rapidez (Redis).

8.5.2 Esquema Nacional de Seguridad (ENS)

Nota📋 Marco de referencia
  • Guías
    • CCN-STIC 803. Valorización de los sistemas en el ENS
  • Temas
      1. ENS

El Esquema Nacional de Seguridad (ENS) es una pregunta permanente en todos los ejercicios prácticas del CSSTIAE.

Las categorías de seguridad del ENS son:

  • Básica
  • Media
  • Alta

Las dimensiones de seguridad del ENS son:

  1. Confidencialidad
  2. Integridad
  3. Disponibilidad
  4. Autenticidad
  5. Trazabilidad

Se asigna a cada dimensión de seguridad una de las categorías. La más alta categoría obtenida en todas las dimensiones determina la categoría global del sistema.

A la hora de evaluar los ejercicios, se debe vigilar cuándo poner categoría alta, pues está reservada a sistemas de información que manejan datos de especial sensibilidad, como los relacionados con la seguridad nacional, la defensa, la seguridad pública y la salud pública.

También se debe vigilar cuándo poner categoría básica, pues está reservada a sistemas de información que manejan datos de baja sensibilidad, como los relacionados con la publicidad, la meteorología o la cultura. Un sistema que almacena datos personales no puede tener categoria básica.

Como referencia sobre cómo categorizar la seguridad del ENS, se puede mencionar la guía CCN-STIC 803 “Valorización de los sistemas en el ENS”.

8.6.2 Reglamento Europeo de la Interoperabilidad (REI)

El Reglamento Europeo de la Interoperabilidad (REI) es también conocido como Interoperable Europe Act (IEA). Se define en el reglamento UE 2024/903

En él se define un Comité de Europa de Interoperabilidad y un Portal de la Europa Interoperable, conocido en inglés como Interoperable Europe portal (antiguo JoinUp).

El REI requiere que se realicen evaluaciones de interoperabilidad en ciertas circunstancias.

Carlos Treviño resume el REI en la 1a parte de la sesión 3 de Preparatic 30, de noviembre 2024, de manera que se puede ver el vídeo y la presentación.

  • Interoperabilidad jurídica
  • Interoperabilidad organizativa

  • Interoperabilidad técnica

8.6.4.2 Dimensiones del ENI

Dimensiones del ENI:

  • Dimensión legal
  • Dimensión organizativa
  • Dimensión semántica
  • Dimensión técnica

8.6.4.3 Instrumentos del ENI

Existen los siguientes inventarios:

  • SIA
  • DIR3
  • CISE
  • CTT

Los dos primeros (SIA y DIR3) trabajan la dimensión/nivel organizativa (al inventariar procesos y organismos, respectivamente), CISE trata la semántica (al inventariar modelos de datos) y CTT la técnica (al inventariar productos y servicios digitales).

Es importante dejar claro en el ejercicio práctico y durante las preguntas de la lectura de que para el sistema se contratan servicios de desarrollo, no de personal.

La metodología Métrica v3, en su documento de Participantes, define una serie de perfiles de participantes en el desarrollo de sistemas de información:

  • Directivo
  • Jefe de Proyecto
  • Consultor
  • Analista
  • Programador

Adicionalmente, en algunos pliegos contemporáneos (como este) se menciona adicionalmente el perfil de analista-programador. Este perfil mixto no figura en Métrica v3 pero sí se aparece en el XII Convenio Colectivo Estatal de Empresas de Consultoría y Planificación de 2000, lo cual puede ser una posible explicación sobre su uso.

Con respecto a categoría y tarifa, esta guía considera análogos los perfiles de analista y analista-programador, justificándose en que en Métrica v3 no existe el perfil mixto.

A efectos prácticos, para puede establecer que un desarrollo necesita el siguiente número de perfiles:

  • 1 jefe de proyecto por proyecto
  • Tantos analistas-programadores como sea necesario para tener el proyecto en la fecha indicada en el enunciado o en un periodo razonable (6-18 meses).
  • Analistas en un ratio de 0,25-0,5 respecto al número total de programadores.
  • Opcionalmente 1 o 2 consultores, en función del presupuesto disponible.

Se suele reducir el ratio de analistas por programador cuando interesa reducir el coste de desarrollo.

También se puede convertir a un analista en analista-programador cuando interese aumentar el número perfiles de programadores sin reducir el ratio de analistas por cada programador.

Este criterio está basada en la definición de Unidad de Trabajo de la licitación de los Servicios de Desarrollo y Mantenimiento del Registro Único de Protonterapia (RUP) para el Sistema Nacional de Salud, donde se definía que una unidad de trabajo estaba formada por:

  • 1 jefe de proyecto
  • 3 analistas
  • 6 analistas-programadores

Otro criterio es suponer que un proyecto típico tiene 12 personas: 1 jefe de proyecto, 2 analistas y 8 programadores. Adicionalmente se puede poner 1 consultor, jugando con esto en función del presupuesto disponible.

8.9.2.2 Mixto

En el contrato mixto se recogen varios objetos de contratación.

En caso de contrato mixto, se distingue entre la preparación y adjudicación del contrato, donde se recogen las normas que establecen las Directivas, y los efectos y extinción.

Respecto de la preparación y adjudicación, la regla general es que al contrato mixto se le aplican las normas del contrato cuya prestación sea la principal o cuyo valor estimado sea más elevado.

8.9.3 Regulación armonizada SARA

La regulación armonizada (SARA) es una regulación que se aplica solamente a contratos que cumplen ciertas características.

La regulación armonizada sre aplica cuando el valor estimado del contrato sobrepasa el umbral de:

143.000 € para la AGE en contratos de suministros y servicios

221.000 € para organismos distintos a la AGE en contratos de suministros y servicios

5.538.000 € en contratos de obras, concesión de obras y de concesión de servicio (para cualquier organismo

Estos importes se establecen en la Orden HFP/1352/2023.

Una de las implicaciones de la regulación armonizada es que los contratos bajo la misma deben publicarse en el Diario Oficial de la Unión Europea.

8.9.6.10 Contratos centralizados

Los contratos centralizados son aquellos que se sirven a todas las administraciones públicas en un único contrato.

En el caso de telecomunicaciones existen 4 lotes:

  • Lote 1. Fijo. Adjudicado a Telefónica
  • Lote 2: Móviles. Otorgado a Vodafone
  • Lote 3: Internet. Otorgado a Telefónica.
  • Lote 4: Internacional. Adjudicado a British Telecom (BT)

8.9.7 Modificación de Contratos

Los pliegos de cláusulas administrativas particulares deben advertir expresamente la posibilidad de modificación y el importe de esta no podrá superar el veinte por ciento del precio inicial del contrato.

8.9.7.1 Encargos a medios propios

Los encargos a medios propios son mecanismos para que se hagan encargos a organismos relacionados con la AGE.

Las encomiendas de gestión no hay una relación vinculante entre encomentante y encomendado.

Son disitntos los encargos a medios propios y las encomiendas de gestión.

La definición de medio propio incluye:

No tener inversión privada.

No tener más de un 20% de actividad en sector privado.

Un ejemplo de medio propio sería la Fábrica Naciona de Moneda y Timbre-Real Casa de la Moneda (FNMT-RCM).

8.9.8 Anuncios de licitaciones público

Los procedimientos negociados sin publicidad no se publican.

El resto de licitaciones se anuncian en la Plataforma de Contratación del Sector Público.

Las licitación de organismos de la AGE se publican además en el Boletín Oficial del Estado.

Las licitaciones sujetas a regulación armonizada (SARA) se publica en el Diario Oficial de la Unión Europea.

8.9.9 Procedimiento general de contratación TIC

Pasos técnicos:

  1. Análisis de necesidades
  2. Especificaciones ténico-funcionales
  3. Evaluación y selección de ofertas
  4. Validación y pruebas

Actividades del análisis de contratación:

  1. Planificación de la capacidad del S.I.
  2. Decisiones HW / SW
  3. Decisiones sobre la rentabilidad económica

Estos tres puntos se desarrollan en los temas 2023.40, 2024.41 y 2024.42 de TIC, que no sueen entrar mucho.

Expediente de contratación:

  • Memoria
  • Certificado
  • Pliegos
    • Pliego de Cláusulas Administrativas Particulares (PCAP).
    • Pliego de Prescripciones Técnicas (PPT).
  • Informes preceptivos de la Memoria y de los Pliegos
    • Para el PCAP, lo realiza el servicio jurítico de la abogacía del estado
    • La memoria y el PPT lo realiza el SGAD
  • Informe de fiscalización por la Intervención Delegada

El Pliego de Cláusulas Administrativas general (PCAG) consta de unas diapositivas.

El PCAP tiene carácter legal y contractual.

En la administración pública nunca se contratan personas. Se contratan solamente servicios y se necesitan personas para cubrir esos servicios.

En caso de retraso en al ejecución del contrato en proporción de 0,60 € por cada 1.000 €. En caso de que se supere el 5% del total se puede rescindir el contrato.

Hay un proceso de recepción de la inversión. En ella está involucrado un técnico gestor.

Corenet es una aplicación de la Intervención General de la Administración del Estado (IGAE) para revisar la recepción de contrato de más de 50.000 € a través de un interventaror de la IGAE. Suele ser un perfil TIC dentro de este organismo.
