8  Supuesto práctico

Las preguntas más habituales en el supuesto práctico sonL

  • Arquitectura lógica
  • Solución tecnológica
  • ENS
  • Arquitectura física
  • Planificación temporal
  • Metodología de desarrollo

Un proceso general sería:

Modelado → Dimensionamiento → Costes → Contratación → Planificación temporal

Si bien el ejercicio suele incluir en primer lugar los pasos relacionados con estos procesos y deja para el final preguntas relacionadas con infraestructuras comunes, servicios transversales, seguridad, interoperabilidad y tecnología, en esta documentación se introducen estos temas solamente tras el modelado ya que es posible que estas decisiones afecten a algún aspecto de la planificación y al fin y al cabo el candidato puede completar los ejercicios en el orden que considere oportuno.

Un ejemplo de decisiones que reducen el esfuerzo de desarrollo la aplicación de servicios comunes ya desarrollados o la aplicación de infraestructuras de nube.

8.2.1.1 Diagrama de casos de uso

Nota📋 Marco de referencia
  • Temas
      1. Análisis de sistemas y metodologías ágiles
  • Referencias
    • Métrica v3. PAe.
    • Cillero, Manuel. Casos de uso en Métrica 3.

El diagrama de casos de uso representa gráficamente los distintos casos de uso de un sistema, así como los actores que interactúan con él.

Los actores se corresponden con tipologías de usuarios, organismos o sistemas externos que interactúen con el sistema.

Los casos de uso se corresponden con las funcionalidades del sistema detectadas.

La relación «include» entre casos de uso se representa con una flecha discontinua y apunta desde el caso de uso que incluye hacia el caso de uso incluido. Indica que el caso de uso incluido es obligatorio para el caso de uso que incluye. Un ejemplo es que para realizar una compra (incluye) es necesario realizar el pago (incluido).

Se puede usar cuando una funcionalidad es común a varios casos de uso, y se quiere evitar repetirla en cada caso de uso.

La relación «extend» entre casos de uso se representa con una flecha discontinua y apunta desde el caso de uso que extiende hacia el caso de uso extendido. Indica que el caso de uso es opcional para el caso extendido, y que se ejecuta bajo ciertas condiciones. Un ejemplo es imprimir un recibo (extensión) tras realizar una compra (extendido).

El sistema engloba los casos de uso, representándose con un rectángulo.

Consejos:

  • Incluir alguna relación «include» y «extend» entre casos de uso, para demostrar al tribunal la capacidad de trabajar con estos conceptos.

8.2.1.2 Diagrama de flujo de datos

Nota📝 Apariciones en examen

Convocatorias/tareas: 2018.1

Nota📋 Marco de referencia
  • Temas
      1. Análisis dinámico de sistemas
  • Referencias
    • Cillero, Manuel. Diagrama de Flujos de Datos en Métrica 3

Diagrama de Flujo de Datos (DFD) es un diagrama que representa el flujo de información entre los distintos elementos de un sistema.

El DFD consta de varios niveles de detalles, numerados de 0 a n, donde 0 es el nivel más alto y n es el nivel más bajo. El nivel 0 es conocido como diagrama de contexto, y representa el sistema como un único proceso que interactúa con elementos externos. Los niveles 1 a n van aumentando el nivel de detalle del sistema y procesos de manera jerárquica.

Ventajas del uso de la nube:

  • Elasticidad
  • Rapidez en el despliegue

Desventajas del uso de la nube:

  • Costes recurrentes
  • Seguridad

En caso de optar por la nube, se considera acertado el uso de NubeSARA, una nube híbrida exclusiva para el ámbito de las AAPP y gestionada desde la AGE.

Las soluciones basadas en otros hiperescalares comunes (Azure, AWS o GCP), si bien tienen cierta presencia en la AGE, solo tiene usos muy determinados y generalmente chocan con cuestiones sobre soberanía del dato, seguridad nacional y privacidad, por lo que su propuesta no se considera generalmente una buena opción.

8.8.1 Esquema Nacional de Seguridad (ENS)

Nota📝 Apariciones en examen

Convocatorias/tareas: 2023.2, 2022.2, 2020.2, 2019.3, 2018.2

Nota📋 Marco de referencia
  • Regulación:
    • RD 311/2022. ENS
  • Guías:
    • CCN-STIC 803. Valorización de los sistemas en el ENS
  • Temas:
      1. ENS

El Esquema Nacional de Seguridad (ENS) es una pregunta permanente en los ejercicios prácticas del CSSTIAE, ya sea por mención expresa o necesidad de considerarla en los diseños. Se suele preguntar expresamente a través de la categorización del sistema y los mecanismos de seguridad aplicables.

Las categorías de seguridad del ENS son:

  • Básica
  • Media
  • Alta

Las dimensiones de seguridad del ENS son:

  1. Confidencialidad
  2. Integridad
  3. Disponibilidad
  4. Autenticidad
  5. Trazabilidad

Se asigna a cada dimensión de seguridad una de las categorías. La más alta categoría obtenida en todas las dimensiones determina la categoría global del sistema.

A la hora de evaluar los ejercicios, se debe vigilar cuándo poner categoría alta, pues está reservada a sistemas de información que manejan datos de especial sensibilidad, como los relacionados con la seguridad nacional, la defensa, la seguridad pública y la salud pública.

También se debe vigilar cuándo poner categoría básica, pues está reservada a sistemas de información que manejan datos de baja sensibilidad, como los relacionados con la publicidad, la meteorología o la cultura. Un sistema que almacena datos personales no puede tener categoria básica.

Como referencia sobre cómo categorizar la seguridad del ENS, se puede mencionar la guía CCN-STIC 803 “Valorización de los sistemas en el ENS”.

Las medidas de seguridad del ENS se detallan en el anexo II del RD 311/2022. Se dividen en tres grupos:

  • Marco organizativo (org)
  • Marco operacional (op)
  • Medidas de protección (mp)

El listado de mecanismos del ENS es el siguiente:

  • Marco organizativo (org)
    • Política de seguridad
    • Normativa de seguridad
    • Procedimientos de seguridad
    • Proceso de autorización
  • Marco operacional (op)
    • op.pl. Planificación
      • Análisis de riesgos
      • Arquitectura de Seguridad
      • Adquisición de nuevos componentes
      • Dimensionamiento/gestión de la capacidad
      • Componentes certificados (n.a. básica)
    • op.acc. Control de acceso

La arquitectura lógica, también referida en algunos ejercicios como modelo lógico o arquitectura de sistema (en singular), representa las distintas capas que posee el sistema.

La arquitectura lógica suele incluir:

  • Actores
  • Dispositivos de usuario (portátil, móvil, etc.)

como seguridad, interoperabilidad, orquestación o accesibilidad.

  • Seguridad

  • Administración

    • Monitorización

Un API gateway (pasarela API) es un bloque que se encuentra entre los dispositivos de usuario y el servidor de presentación, y que se encarga de gestionar las solicitudes de los usuarios hacia las APIs del sistema.

Una aplicación de móvil se conecta directamente con el backend, ya que es la app instalada en el móvil quien lleva la carga del frontend.

Arquitectura hexagonal

Considera tres capas:

  • Aplicación
  • Adaptadores
  • Sistemas externos

La capa de aplicación contiene la lógica propia del dominio. Excluye cualquier referencia a interfaces, tecnologías o sistemas externos.

La capa de adaptadores sirve de adaptación entre los sistemas externos y la aplicación. En el borde exterior de esta capa se encuentran los puertos, que son interfaces abstractas entre los sistemas externos y la aplicación. Los adaptadores son implementaciones de estos puertos.

Una de las particularidades de esta arquitectura es que considera a las bases de datos actores, ya que se considera dependiente de tecnología, intercambiable y por tanto externa al dominio.

Los puertos y adaptadores pueden ser primarios y secundarios. Los adaptadores primarios son los que permiten a los actores o sistemas externos interactuar con la aplicación, mientras que los adaptadores secundarios son los que permiten a la aplicación interactuar con actos externos.

La capa de sistemas externos considera los actores y sistemas fuera del control del sistema gestionado.

En la arquitectura lógica debería representarse cada adaptador entre la aplicación como un recuadro distinto.

Una arquitectura de red o red de comunicaciones suele incluir los siguientes elementos:

  • Enrutadores (router)
  • Cortafuegos
  • WAF
  • Balanceadores
  • Switches
  • Proxy (forward proxy)
  • Proxy inverso (reverse proxy)
  • Redes de área local (LAN)
  • VPNs
  • DNS
  • CDN
  • Conexión con otras redes (redSARA, sTESTA)
  • VLAN

Hay varias arquitecturas de red privada posibles, y una bastante habitual es la del cortafuegos dual. Esta consiste en segmentar la red privadas en dos:

  • Red perimetral, en ocasiones llamada subred apantallada o zona desmilitarizada (demilitarized zone, DMZ), expuesta a una red externa a través de un cortafuegos externo o perimetral y que alberga a los servidores públicos.
  • Red privada, expuesta a la red perimetral a través de un cortafuegos interno, y que aloja servidores y equipos privados.

A la hora de aplicar VLANs, una posible segmentación sería:

  • Servidores de presentación
  • Pasarelas / Middleware

El enrutador (router) coloca en la parte más externa de la red perimetral para conectarse con otras redes, ya sea internet o intranets como red SARA. Se empleará un enrutador distinto para cada red conectada. Además, por seguridad que requiere que los enrutadores estén duplicados.

Algunos aspirantes sustituyen el enrutador hacia la red SARA por un elemento llamado Acceso de Conexión (AC).

Los enrutadores suelen ser los últimos elementos que pertenecen a la red del organismo de la AGE gestionado.

Se coloca por tanto un cortafuegos (firewall) detrás de cada enrutador da acceso a la red privada. Los cortafuegos se colocan en pares con característicias y configuración idéntica para asegurar que si falla uno el otro se encuentra disponible. No obstante, se suele recomendar que el interno y el externo sean de fabricantes distintos, para asegurar en caso de que uno de ellos tenga una vulnerabilidad explotable que no sea posible acceder a la red apantallada.

Los candidatos suelen configurar el par de cortafuegos externo como activo-pasivo y el par de cortafuegos interno como activo-activo.

Varios enrutadores pueden emplear un mismo cortafuegos si este tiene libres interfaces de red o soporta VLANs. Los aspirantes habitualmente utilizan el mismo cortafuegos interno para conectar tanto el enrutador a las intranets como la red privada.

El cortafuegos externo tendrá una conexión directa con el cortafuegos interno.

Cada cortafuegos (o par de cortafuegos) suelen ir acompañados de un IPS o un IDS. Algunos aspirantes colocan un IDS con el cortafuegos externo y un IPS con el cortafuegos interno. Otros aspirantes colocan un único IPS en mitad de la connexión entre el cortafuegos externo y el interno. El IPS es mencionado como elemento necesario en el ENS.

La VPN debe estar disponible en caso de que haya usuarios que deban acceder a la red interna a través de la VPN. Se debe adaptar al [mp.com.2] del ENS. Para sistemas de categoría media estas VPN deberán utilizar algoritmos y parámetros autorizados por el CCN (refuerzo R1). Si se trata de sistemas de categoría alta, además, se debe utilizar un dispositivo hardware certificado para el establecimiento y utilización de la VPN (refuerzos R2 y R3).

El cortafuegos interno, como se comentó, estará conectado a otras intranets (como red SARA) y a la subred apantallada.

Se representan como nubes las WLANs como red SARA y otras intranets:

  • La red sTESTA se suele representar como otra nube conectada a SARA, ya que la conexión con sTESTA a través de la red SARA.
  • Las redes de comunidades autónomas (CCAA) se conectan con la red SARA, nunca directamente al organismo de la AGE.
  • Las redes de entidades locales (EELL) siempre están conectadas a redes de comunidades autónomas (CCAA), nunca se conectan directamente a red SARA.

Los servicios comunes y transversales de las AAPP se ofrecen a través de la red SARA.

En la red perimetral, conectados directamente con el cortafuegos exterior, suelen estar presentes:

  • Sonda SAT-inet
  • VLAN 10: tráfico entrante
    • Servidores de proxy inverso
    • Balanceadores
    • Servidor DNS
  • VLAN acceso externo:
    • Servidores VPN
  • VLAN tráfico saliente:
    • Servidores proxy
  • VLAN presentación:
    • Servidores de presentación / web
  • VLAN middleware:
    • API Gateway

La sonda SAT-inet (acrónimo de Sistema de Alerta Temprana de Internet) es un elemento de monitorización que permite al CCN monitorizar la red del organismo de la AGE.

La sonda SAT-inet se suele colocar en la red perimetral, conectada fuera de banda (out-of-band) a un puerto SPAN o Mirror del switch core o del cortafuegos, de manera que reciba una copia del tráfico para analizarlo de forma paralela. Es importante recalcar que NO corta el tráfico.

El balanceador puede software o appliance.

8.12.1 Tecnologías según contexto

8.12.1.1 Lenguajes de programación

El lenguaje de programación más empleado en la AGE para servidores back-end y aplicaciones de escritorio (este último en declive) es Java.

Para servidor front-end, TypeScript (con el framework Angular) seguido por JavaScript (con el framework React) son los lenguajes más empleados.

.NET también tiene una presencia importante en la AGE.

8.12.1.2 Tecnología web front-end

La tecnología web front-end más empleada en la AGE es Angular, que emplea el lenguaje de programación TypeScript. Se usa para aplicación grandes.

A cierta distancia, la segunda tecnología más utilizada es React, que emplea el lenguaje de programación JavaScript. Se usa para aplicaciones híbridas y con interfaz cambiante y muy interactivos.

Bootstap se usa también de manera minoritaria para aplicaciones web o móvil con interfaz sencilla.

8.12.1.3 Tecnología web back-end

El framework Spring Framework, o su alternativa Spring Boot, que emplea el lenguaje de programación Java, es el estándar en la AGE.

8.12.1.4 Aplicaciones de escritorio

Antes de proponer una aplicación de escritorio en el supuesto práctico se debe reflexionar, pues la tendencia actual en la AGE es priorizar aplicaciones web sobre software de escritorio tradicional. Por ello, para proponer una aplicación de escritorio se debe justificar por la necesidad de una fuerte integración con el sistema operativo o hardware (ej.: lector de tarjetas), la necesidad de un rendimiento muy alto o la necesidad de una interfaz muy compleja.

Las aplicaciones de escritorio con tecnologías .NET, del entorno de desarrollo de Microsoft y escritas en C#, son también populares en la AGE.

La AGE ha empleado históricamente Java con la biblioteca UI Swing para aplicaciones desarrolladas exclusivamente para escritorio, como por ejemplo AutoFirma. No obstante, proponerlo para una nueva aplicación puede considerarse una mala práctica al considerarse tecnología obsoleta.

Un enfoque alternativo y moderno es adaptar una aplicación web como aplicación de escritorio empleando tecnologías web híbridas empleando el framework Angular (o React, como opción alternativa) sobre el framework web Electron; Tauri sería también técnicamente válida como ventana de navegación interna (webview), pero es más experimental y no está tan extendido en la AGE.

8.12.1.5 Aplicaciones de móvil

Se puede consultar las tecnologías de las aplicaciones móviles en el inventario de aplicaciones móviles del OBSAE.

Se concluye leyendo este informe que las aplicaciones móviles de la AGE están realizadas principalmente con Ionic, Angular y Flutter, en orden descendente.

Ionic proporciona componentes específicos para móvil adaptados a cada SO y se basa en un WebView, es decir, una web inscrustada en una app de móvil. Puede combinarse con Angular u otro framework web o ejecutarse independientemente.

Angular es una buena opción si es necesaria una misma app para web y móvil. Es conveniente que esta web sea responsiva (se adapta a la pantalla con fluidez) o adaptativa (considera distintas configuraciones y escoge la más adecuada), lo cual se consigue con frameworks CSS como Bootstrap o Tailwind CSS.

Para la solución basadas en WebView (como Angular y Ionic), se puede emplear Capacitor (el reemplazo de Apache Cordova) como puente entre el dispositivo móvil y la ventana de navegación interna (WebView) en la que se ejecuta la app web de Angular. Proporciona acceso al hardware y permite al usuario mostrar la aplicación como una app.

Flutter ejecuta código nativo en lugar de estar basado en tecnologías web (como Angular e Ionic), lo que le da mayor rendimiento.

8.12.1.7 Contenedores y orquestación

Para mensajería e integración en la AGE se emplen herramientas de código abierto como RabbitMQ o Apache Kafka.

8.12.1.9 API manager

Una opción propietaria de API manager (o gestor de APIs) habitual en la AGE es MuleSoft AnyPoint Platform.

8.12.2 API gateway

La funcionalidad de API gateway (o pasarela de APIs) está habitualmente incluida en las suites de API manager. Por ello, si el sistema ya cuenta con un API manager, no es necesario implementar un API gateway adicional.

Por ejemplo, MuleSoft AnyPoint Plaform incluye MuleSoft API Gateway, mientras que WSO2 API Manager incluye WSO2 API Gateway.

Una opción de código abierto centrada en la funcionalidad de API gateway es Kong API Gateway Community Edition (CE). El API manager completo Kong Manager sería de pago.

8.12.3 Stack de tecnologías

Se conoce como stack a la combinación de combinación de tecnologías empleada en un sistema. A la hora de proponer el stack en el supuesto práctico, se debe reflexionar cuál es el más adecuado en base a distintos criterios.

Hay combinaciones de tecnologías encontradas con más frecuencia que otras. Por ejemplo, es habitual encontrar Angular para el front y Spring Boot para el backend, mientras que es menos habitual encontrar Angular para el front y .NET para el backend. Puesto que se busca un sistema maduro y estable, conviene sugerir un stack habitual.

Otro criterio importante es la elección de stacks ya habituales en la AGE, con la ventaja de contar con familiaridad en la institución y el facilitar la búsqueda de perfiles relacionados.

A continuación se proponen tres ecosistemas o stacks de tecnologías habituales:

  • Pro-Oracle
  • Pro-Microsoft
  • Pro-código abierto

8.12.3.1 Pro-Oracle

Stack genérico empleando tecnologías propias del ecosistema Oracle:

  • Framework frontend: Angular (TypeScript)
  • Servidor web: Oracle HTTP Server
  • Framework backend: Spring Boot (Java)
  • Servidor aplicación: Oracle Weblogic
  • Base de datos: Oracle Database

Angular no es nativo del ecosistema Java o pro-Oracle, pero está bien integrado en él y suele ser una opción habitual. Oracle JET sería el framework frontend nativo de Oracle, pero este no es tan popular en la AGE como Angular.

Una alternativa también común en la AGE a Oracle Weblogic es IBM WebSphere, ambos propietarios.

8.12.3.2 Pro-Microsoft

El ecosistema pro-Microsoft tiene cierta presencia en la AGE, si bien no es ubicua.

Sugerencia de stack genérico empleando tecnologías propias del ecosistema Microsoft:

  • Framework frontend: ASP.NET (C#)
  • Servidor web / aplicación: IIS (Windows Server)
  • Framework backend : .NET
  • Framework escritorio: WPF
  • Framework móvil: .NET MAUI
  • Base de datos: Microsoft Server SQL

Como alternativa más moderna al framework frontend se puede usar Blazor, que permite crear aplicaciones web interactivas con C#. No obstante, de momento Blazor es poco popular en la AGE respecto a ASP.NET, pero sobre todo respecto a Angular o React.

Se propone Windows Presentation Foundation (WPF) como framework de escritorio, con la nota de que la tendencia actual de la AGE es ofrecer interfaces web en lugar de aplicaciones de escritorio. La tecnología Windows Forms (WinForms) está presente en la AGE como legacy, y no sería adecuada para nuevos sistemas.

Se propone .NET MAUI (sucesor de Xamarin) como framework de aplicaciones móviles del ecosistema pro-Microsoft, si bien no es usado habitualmente en la AGE.

8.12.3.3 Pro-código abierto

Propoponer un stack de código abierto otorga la ventaja de evitar costes de licenciamiento (reduciendo costes y poder agilizar los plazos de contratación) y eliminar la dependencia del proveedor (vendor lock-in).

  • Framework front: Angular (TypeScript)
  • Servidor web: Apache HTTP Server / Nginx (contenedores)
  • Framework backend: Spring Boot (Java)
  • Servidor aplicación: RedHat WildFly (monolítico) / Apache Tomcat (microservicios)
  • Base de datos: PostgreSQL

User Case Points (UCP)

Los puntos de caso de uso (use case points, UCP), a veces referidos como el método Karner, es un método de estimación de software basado en la complejidad de los casos de uso. Es por tanto adecuado cuando el supuesto práctico pide realizar un diagrama de caso de uso además de la estimación.

Fue desarrollado por Gustav Karner en 1993 mientras trabajaba en la compañía sueca Objectory Systems.

Hay un buen ejemplo en la Wikipedia.

El total de puntos de casos de uso se calcula mediante la siguiente fórmula: \[\text{UCP} = \text{UUCP} * \text{TCF} * \text{ECF}\]

Los puntos de casos de uso sin ajustar (Unadjusted Use Case Points, UUCP) se calculan como:

\[\text{UUCP} = \text{UUCW} + \text{UAW}\]

por lo que

\[\text{UCP} = (\text{UUCW} + \text{UAW}) * \text{TCF} * \text{ECF}.\]

El peso de caso de uso sin ajustar (Unadjusted Use Case Weight, UUCW) se calcula como:

Use Case Classification No. of Transactions Weight
Simple 1-3 5
Average 4-7 10
Complex ≥8 15

\[UUCW = \sum{\text{no. de casos de usos} \times \text{peso}}\]

El peso de actor sin ajustar (Unadjusted Actor Weight, UAW) se calcula como:

Actor Classification Type of Actor Interaction Weight
Simple API 1
Average Communication protocol 2
Complex GUI 3

\[UAW = \sum{\text{no. de actores} \times {peso}}\]

El factor de complejidad técnica (technical complexity factor, TCF) depende de la complejidad de la solución.

El factor de complejidad de ambiente (environmental complexity factor, ECF) depende de la experiencia del equipo de desarollo.

En un ejercicio completo se emplearían tablas y fórmulas para calcular el TCF y el ECF. De cara al ejercicio práctico, puesto que no se dispone de una copia de las tablas y fórmulas, calculadora y tiempo suficiente, para facilitar las cuentas se puede considerar que el TCF y el ECF son 0.8 y 1.25 (en el orden indicado, ya que son sus valores medios) para obtener un producto de 1 y facilitar las cuentas.

Una vez obtenidos los UCP, estos se transforman a horas. Puede ser tan sencillo como considerar un número de hroas fijos por caso de uso.

COSMIC-FSM
Nota📋 Marco de referencia

COSMIC-FSM es una técnica de dimensionamiento funcional basada en el comportamiento del software y el movimiento de datos. La principal ventaja de COSMIC-FSM es que no requiere haber modelado previamente el caso.

El Consorcio Internacional de Medidas de Software Común (Common Software Measurement International Consortium, COSMIC) fue creada in 1998. Adaptó la idea de IFPUG FPA a las nuevas tendendicas de desarrollo, dando lugar a la técnica de COSMIC-FSM. Se ha estandarizado bajo el estándar ISO/IEC 19761, siendo la última versión ISO/IEC 19761:2011.

La técnica consiste en contar el total de puntos de función COSMIC (COSMIC function points, CFP) en un sistema, donde se cuenta 1 CFP por cada elemento de esta tipología encontremos:

  • Entrada
  • Salida
  • Lectura
  • Escritura

El método requiere que se cuenten con proyectos anteriores para los que sea conocido sus CFPs, coste y duración total, de manera que se pueda aplicar una regla de tres para calcular el tiempo o el coste dados los CFPs del nuevo proyecto.

\[ t_2 = \frac{\text{CFP}_2 \times t_1}{\text{CFP}_1} \]

\[ c_2 = \frac{\text{CFP}_2 \times c_1}{\text{CFP}_1} \]

Puesto que es poco probable de que en el supuesto práctico del CSSTIE contemos con información sobre rendimiento por CFP en base a proyecto anteriores, si queremos emplear esta técnica debemos suponer un coste y duración por CFP estimados. Por ejemplo, 1 CFP puede corresponder con 10 horas de trabajo (aunque en el ejemplo de la bibliografía de Astic 1 PF = 100).

Por otro lado, el coste se puede obtener directamente conviertiendo los CFPs en horas empleando un coeficiente supuesto (ej. 1 CPF = 1.000 €), o si no de forma más compleja, pues que ya se tiene el número de horas de trabajo por la suposición anterior, aplicar las tarifas de los empleados.

  • Tantos analistas-programadores como sea necesario para tener el proyecto en la fecha indicada en el enunciado o en un periodo razonable (6-18 meses).
  • Analistas en un ratio de 0,25-0,5 respecto al número total de programadores.
  • Opcionalmente 1 o 2 consultores, en función del presupuesto disponible.

Se suele reducir el ratio de analistas por programador cuando interesa reducir el coste de desarrollo.

También se puede convertir a un analista en analista-programador cuando interese aumentar el número perfiles de programadores sin reducir el ratio de analistas por cada programador.

Este criterio está basada en la definición de Unidad de Trabajo de la licitación de los Servicios de Desarrollo y Mantenimiento del Registro Único de Protonterapia (RUP) para el Sistema Nacional de Salud, donde se definía que una unidad de trabajo estaba formada por:

  • 1 jefe de proyecto
  • 3 analistas
  • 6 analistas-programadores

Otro criterio es suponer que un proyecto típico tiene 12 personas: 1 jefe de proyecto, 2 analistas y 8 programadores. Adicionalmente se puede poner 1 consultor, jugando con esto en función del presupuesto disponible.

8.17.1 Proceso de contratación en supuesto práctico

Pasos del proceso de contratación en el supuesto práctico:

  1. Asignar cada uno de los gastos a una tipología de contratación según objeto (ej.: suministros, servicios)
  2. Comprobar si aplica la tramitación urgente
  3. Incluir todos los gastos posibles en contratación centralizada (ej.: AM, SDA).

  5. Dividir en lotes
  6. Comprobar si el contrato está sujeto a regulación armonizada (SARA), y en caso afirmativo, explicar implicaciones.
  7. Comprobar si el contrato debe ser aprobado por Consejo de Ministros (>12M€).

Evaluación del proceso de contratación: - Escoger el proceso de contratación más simplificado y rápido disponible. - Si se aplica trámite de urgencia permiten reducir a la mitad los tiempos, si bien no se pueden reducir tiempos de los periodos de alegaciones.

8.17.7 (Paso 5) Regulación armonizada SARA

La regulación armonizada o SARA es aquella se aplica a contratos del sector público de la UE que cumplen ciertas condiciones. Estas están especificadas en la Sección 2.ª “Contratos sujetos a una regulación armonizada” (a partir del artículo 19) la LCSP. Esta parte suele ser actualizada regularmente mediante órdenes. En 2026, la última orden aplicada fue la Orden HAC/1517/2025.

Un contrato de regulación armonizada o contrato SARA es aquel sobre el que se aplica la regulación armonizada.

Condiciones SARA

Desde 2026, SARA se aplica cuando el valor estimado del contrato sobrepasa el umbral de:

  • 140.000 € para la AGE en contratos de suministros y servicios
  • 216.000 € para organismos distintos a la AGE en contratos de suministros y servicios
  • 750.000 € para contratos de servicios sociales y especiales especificados en el Anexo IV de la LCSP
  • 5.404.000 € en contratos de obras, concesión de obras y de concesión de servicio (para cualquier organismo)

Existen una serie de excepciones en los que no se aplica SARA especificadas en los art. 19.2. De manera muy sintetizada, serían los contratos relacionados con los servicios siguientes:

  • Comunicación audiovisual
  • Defensa
  • Secretos o reservados
  • Comunicaciones
  • Servicios jurídicos
  • Defensa civil, protección civil o gestión de riesgos
  • Transporte público
  • Abastecimiento y tratado de agua

Implicaciones SARA

El resumen de las implicaciones para los contratos bajo regulación armonizada respecto las no SARA son:

  • El anuncio deben publicarse en el Diario Oficial de la Unión Europea (en lugar del BOE).
  • Plazos más largos y pasos adicionales que ralentizan el proceso.
  • Rigidez en las modificaciones.

El procedimiento abierto es el ordinario de contratación. Se le llama en este apartado procedimiento abierto ordinario para distinguirlo de variantes como el simplificado y el abreviado, aunque este no sea su nombre oficial.

El plazo de presentación de proposiciones es:

    • Para contratos de suministro y de servicios, valor estimado <= 140.000 €
  • Criterios de adjudicación
    • En prestación de carácter no intelectual, los juicios de valor deben ser <25%
    • En prestación intelectual, los juicios de valor deben ser <40%

Plazo de presentación de proposiciones mínimo:

  • Obras: 20 días
  • Otros: 15 días

Permite negociar con los licitadores las condiciones, quedando fuera los aspectos esenciales y los criterios de adjudicación.

La versión estándar requiere publicidad.

Solo se puede aplicar en un número de casos:

  • Cuando requiera que los licitadores realicen un trabajo previo de diseño o adaptación.
  • Cuando se trate de una solución innovadoras
  • Cuando las negociaciones sean ineludibles.
  • Cuando el órgano de contratación con puede precisar suficientemente las especificaciones.
  • Cuando no se haya recibido nada aceptable tras realizar un procedimiento abierto o restringido.
  • Cuando se trate de contratos de servicios sociales personalísimos.
Procedimiento negociado sin publicidad

Regulado en el artículo 168 del LCSP.

Es similar al procedimiento negociado estándar pero no requiere publicidad.

Requiere que se de una compleja lista de condiciones, entre ellas:

  • No se haya presentado ninguna oferta; ninguna oferta adecuada; ninguna solicitud de participación; o ninguna solicitud de participación adecuada en respuesta a un procedimiento abierto o a un procedimiento restringido.
  • Cuando las obras, los suministros o los servicios solo puedan ser encomendados a un empresario determinado.
  • Cuando el contrato haya sido declarado

8.17.11.6 Contrato menor

Un contrato menor debe cumplir una serie de condiciones.

Condiciones del contrato menor:

  • Condiciones económicas
    • Contratos de obras: valor estimado < 40.000.
    • Contratos de suministros o servicios: valor estimado < 15.000 €.

En este caso se define también en valor estimado y no al importe base de licitación.

Se debe solicitar al menos 3 prespuestos.

No se requerirá la aprobación del gasto, pero sí la incorporación al expediente de la factura correspondiente.

Los contratos menores NO son susceptbiles de prórroga.

8.18 Planificación temporal

Este apartado trata sobre la planificación de desarrollo de software, que es una tarea habitual en el supuesto práctico del ejercicio práctico del CSSTIAE.

En la planificación temporal hay que tener en cuenta los siguientes factores:

  • Tiempo mínimo de contratación
  • Esfuerzo de desarrollo

8.18.1 Aspectos generales de planificación

El input recibido en la planificación sería:

  • Tiempo de contratación
  • Esfuerzo total del desarrollo

Las variables en el proyecto son:

  • Número de horas totales
  • Número de programadores

El número de horas totales hay que dividirlas entre el número de programadores.

En caso de que hayamos calculado el esfuerzo en días (por ejemplo, al usar staffing size):

  • 1 mes = 20 días laborables
  • 6 meses = 120 días laborables
  • 1 año = 240 días laborales.

En caso de que hayamos calculado el esfuerzo en horas:

  • 1 mes ~ 150 horas
  • 3 meses ~ 500 horas
  • 6 meses = 960 horas ~ 1.000 horas
  • 1 año = 1.920 horas ~ 2.000 horas

Consejos generales:

  • En caso de que se indique un plazo máximo de entregao, asegurarse de que se cumple.
  • En caso de que no se especifique un plazo de desarrollo, tratar que se proponga un plazo de entrega coherente. De manera general, en proyectos de dificultad media habría una expectativa de estar listo en un periodo entre 6 y 12 meses.
  • Algunos aspirantes añaden una o varias fases paralelas que abarcan todo el ciclo de vida del proyecto y que reflejan actividades transversales a todo el proyecto, como la calidad o la seguridad.
  • Factores limitantes del proyecto como la contratación deben quedar reflejadas en la planificación.
  • Tratar de adaptar el diagrama de Gantt al enunciado, por ejemplo añadiendo hitos relevantes del proyecto en el cronograma.
  • Incluir cualquier anotación que sea relevante en el ejercicio escrito, y tratar de no contar con la defensa para anotarlas de manera oral.

8.18.2 Metodologías de desarrollo

Nota📝 Apariciones en examen

Convocatorias/tareas: 2022.4.c, 2019.5, 2018.4

Es necesario especificar una metodología de desarrollo.

En caso de escoger alguna metodología ágil basada en SCRUM, se debe dividir el proyecto en funcionalidad que se estimen que tengan una complejidad y esfuerzo similar y que se puedan completar en sprints de duración 2-4 semanas. De manera práctica y de cara a este ejercicio, muchos candidatos optan por hacerlo en sprints de 2 ó 4 semanas, que son más fáciles de representar en un diagrama de Gantt dividido en meses.

8.18.3 Fases de un proyecto

Nota📋 Marco de referencia
  • Referencias
    • Manuel Cillero, Métrica v3, manuel.cillero.es.

Hay muchos modelos para definir las fases de un proyecto de desarrollo de software. En el supuesto práctico del ejercicio práctico del CSSTIAE se puede aplicar el modelo de Métrica v3, que es el de referencia para la Administración General del Estado (AGE).

Las fases de un proyecto de sistemas informáticos según el Desarrollo de Sistemas de Información de Métrica v3:

  1. Estudio de viabilidad del sistema (EVS)
  2. Análisis del sistema de información (ASI)
  3. Diseño del sistema de información (DSI)
  4. Construcción del sistema de información (CSI)
  5. Implantación y aceptación del sistema (IAS)
  6. Mantenimiento del sistema de información (MSI)

En caso de metodologías tradicionales, estas fases de desarrollo se aplican a la totalidad del proyecto. En caso de metodologías ágiles, las fases 2-5se aplican a cada iteración o sprint y reduciendo a los pasos 2-5, mientras que la fase 1 (EVS) y la fase 6 (MSI) se aplican al inicio y final del proyecto respectivamente.

Es importante también considerar otros procesos necesarios, como la contratación o la formación, que pueden ir de forma paralela a estas fases.

Acciones que se realizan durante la EVS:

  • Memoria justificativa.
  • Revisión del CTT.
  • Estudio de los tipos de licencia.
  • Selección del equipo de usuarios pilotos.
  • Documento de licitación para la contratación.
  • Tipo de migración (si aplica).
  • Formación.

8.18.4 Representación de la planificación temporal

La representación de la planificación debe reflejar el modelo de ciclo de vida y la metodología de desarrollo escogida.

8.19 Realización del supuesto práctico

8.19.1 Material para realizar el ejercicio práctico

Material para llevar:

  • 2 bolígrafos
  • Corrector ortográfico
  • Subrayadores de colores
  • Lapicero
  • Goma de borrar
  • Cuaderno, hojas o portátil para realizar el volcado

No está permitido el uso de calculadora u otro dispositivo electrónico.

En caso de requerir llevar algún dispositivo por razones médicas, consultar las bases, pues es posible que haya que obtener algún tipo de documentación médica y notificar de antemano.

8.19.2 Consejos para el supuesto práctico

Resumen de consejos:

  • Leer las preguntas antes de leer el enunciado completo.
  • Subrayar los conceptos del exámen.
  • Emplear una hoja para cada ejercicio. No penaliza el número de hojas empleadas, y el usar hojas independientes permite alargar la resolución del ejercicio en caso de que se requiera ampliar una respuesta.

En la mayoría de tribunales, si escribes en las hojas del enunciado del supuesto práctico no las podrás sacar posteriormente. No contar con el enunciado dificulta la realización del volcado, por lo que no parece buena práctica realizar algo que nos lo quite.

Por el contrario, emplear subrayadores es compatible con sacar la hoja del enunciado. Algunos candidatos emplean varios colores para marcar distintas categorías de palabras claves, como por ejemplo actores, acciones, etc.

Una propuesta de subrayado de colores puede ser:

Significado Color sugerido
Actor / Sistema Azul
Entidad de datos Verde
Funcionalidad Naranja
Normativa Rojo
Cuestiones de interés Amarillo

Se podría distinguir con distinto color los actores internos y externos.

8.19.3 Simulación del supuesto práctico

Se recomienda simular el supuesto práctico en las condiciones más similares a la situación real.

Algunas academias o preparadores indican que antes de presentarse se deben haber realizado al menos 10 supuestos prácticos.

8.19.4 Enlace con el análisis pormenorizado

Para la siguiente parte, el análisis pormenorizado, se conserva el enunciado del supuesto y una única hoja de notas. En caso de que se quiera retener alguna nota para el análisis pormenorizado, esta debe ser copiada en la hoja de notas facilitada para tal efecto.
